# membrane changelog

Named `claude-security-audit` through 0.3.1.

## 0.8.0 (2026-11-08)

**Hook handler code is now audited (#1136).** HOOK-001 to HOOK-004 read shell only: a script, an executable `.claude/hooks/` file, OpenCode code, a hook command declared in JSON. An enabled plugin's hooks module (`hooks/hooks.json` naming `{"modules": ["./register.ts"]}`) and the node or python handlers kept in its `hooks/` were never read, and a `hooks.json` that holds only `modules` read as no hooks at all: no finding and no count. Expect new findings, on first-party plugins too, the first time you audit after upgrading.

Skill-first (`docs/conventions/skill-first.md`): the handler-file test is question 3, a path test on open input (file names) that can only add a stop. The `modules` read is question 3 too: a third-party JSON manifest's paths are open input, and the read can only add a stop (a path it cannot place is a HOOK-005, never a pass). The four patterns are unchanged and stay question 3. A file this does not read goes to your own reading exactly as before.

### Added
- **HOOK-001 to HOOK-004 read hook handler code** (`csa_hook_handler_file`, `lib/hook-entries.sh`):
  - every `.ts .tsx .jsx .js .mjs .cjs .mts .cts .py` file under an enabled plugin's `hooks/`: a Claude Code hooks module, everything it imports from there, and node or python handlers a hook command runs from there. Not a `.d.ts`, `*.test.*` or `*.spec.*` file, and nothing below `hooks/` under `tests/`, `test/`, `fixtures/` or `node_modules/`;
  - an executable regular file under a plugin's `hooks/` with no code suffix (superpowers' `hooks/session-start` and `hooks/run-hook.cmd`), as an executable `.claude/hooks/` file has been read since 0.1.6. A symlink is not read;
  - code with those suffixes under the project's own `.claude/hooks/`, whatever its mode: a `python3 .claude/hooks/x.py` handler that is not executable was enumerated but never read. `.mjs .cjs .tsx .jsx .mts .cts` there are now enumerated too.
  - The rules' detect bodies, their patterns, HOOK-004's `LC_ALL=C` matching and 0.5.2's boundaries are unchanged. Only the surface that each rule's path gate and the hooks aspect gate accept is wider. A plugin file is judged by the plugin layout alone, so a plugin's `fixtures/` copy of a `.claude/hooks/` is not read in any mode it was not read in before.
- **A plugin's `hooks/hooks.json` `modules` list is read.** Each path resolves relative to the file with the physical containment check a `plugin.json` hooks path gets. A path that resolves to handler code inside `hooks/` is counted, and the module file is read as a target of its own. A path outside `hooks/`, absolute, missing, a symlink, not a string, holding a control character, under `hooks/tests/` or not a code file is a High HOOK-005 finding naming `modules[i]`; a `modules` value that is not a list is one HOOK-005 on `modules`. A `modules` key beside `hooks` leaves the hooks walk as it was. `modules` is read only in a plugin's `hooks/hooks.json`, never in settings or `plugin.json`.
- **A hook file whose name holds a newline or tab is a High HOOK-005, not silently unread.** Such a file anywhere below an enabled plugin's `hooks/` (a `.sh` or `.md` file too), or a code file under the project's `.claude/hooks/` (a non-executable `.ts .tsx .jsx .js .mjs .cjs .mts .cts .py` one, or a `.py .js .ts` one in any mode), cannot be one target line, so it is not read: one HOOK-005 names the file (newline and tab escaped) and, for a plugin, the plugin, and the audit goes on. An executable one there whose suffix the enumeration does not list (`.mjs`, say, or none) still refuses the whole audit, as it has since 0.1.6 (#426).
- **A symlink below a hook dir is a High HOOK-005.** A symlink is never followed, so what it points at is not read, and until now nothing said so. Each symlink below an enabled plugin's `hooks/` (to a file or to a directory, a `hooks.json` among them), a plugin `hooks/` that is itself a symlink, each symlink below the project's `.claude/hooks/`, and a `.claude/hooks/` that is itself a symlink is one High HOOK-005 naming the path and, for a plugin, the plugin. It is not read; every other finding is unchanged. A symlink anywhere else gets no finding, as before.
- **The coverage line counts modules:** `csa: hook-coverage checked=N flagged=N not-inspected=N unreadable=N modules=N`. `modules=N` counts the resolved `modules` entries, not distinct files: two entries naming one file count twice. A modules path that did not resolve counts as unreadable. Neither HOOK-006 nor `not-inspected` counts a module.

### Migration
- **No existing finding changes its uid.** Every target read before is read exactly as before, by the same detect body. A file whose name holds a newline or tab was never read whole, and its finding changes: below a plugin's `hooks/` (a `.sh` file, say) it was a Medium SCANNER-003 on a fragment of its name, and is now one High HOOK-005 on the real name; a `.py .js .ts` one under the project's `.claude/hooks/`, executable or not, was the same Medium SCANNER-003 under a full audit (nothing under `--focus hooks`), and is now the same High HOOK-005. A new finding reads NEW and is suppressed as usual. A plugin finding's uid holds no version (`@plugin:<plugin>@<marketplace>:hooks/x.ts`), so it survives a plugin update.
- A project `.claude/hooks/x.py` that was executable keeps its uid; one that was not is a new finding.
- A symlink below the project's `.claude/hooks/` or an enabled plugin's `hooks/` is a new High HOOK-005 finding. Replace the link with the file, or suppress the finding, to clear it.
- Measured on this host:
  - The existing hook surface (1668 files: the Claude Code and OMP plugin caches, the marketplace clones and every cached membrane copy) gives the same 966 findings, identical in rule, file, line and uid.
  - The new handler files an audit reads gives **0 new findings**. That corpus is the 40 code files under a cached plugin's `hooks/` (enabled seat-mods 0.15.3 and molt 0.5.0 among them) plus superpowers 7.0.0's two suffix-less handlers, and the handler-file test reads all 42.
  - A hooks scan of the three enabled plugins prints `modules=2` and gives no finding.
  - The four patterns over all 121 code copies under a `hooks/` (both caches and the clones) hit 1 file: security-guidance's `hooks/llm.py`, a review prompt naming `/etc/passwd`, curl and ssh. It is a false positive in a clone that is not installed.

### Known limits
- **Code-shaped forms stay silent; they need judgment, not a pattern.** These are `fetch`, `requests` or `$.http.fetch` sending a file read, a path built with `homedir()`, `expanduser` or concatenation, an argv `rm` (`$.process.run(['rm', '-rf', '/'])`), `fs.rmSync` and `shutil.rmtree`, `eval(`, `exec(` and `new Function`, and a command name split across strings. The rules read a command written as a string, or as quoted argv words for HOOK-004.
- **A guard, a prompt or a comment that names the danger it looks for fires**, as a comment in a script already does. Examples: `const DENY = ['~/.ssh']` beside a quoted `'ssh'`, a review prompt naming `/etc/passwd`, `// never curl … | sh`, and test data inside a handler (`{command: "rm -rf /tmp/x"}`).
- **A handler outside `hooks/` is not read**, such as codex's `scripts/*.mjs`; the command that runs it is still checked. A file a module imports from outside `hooks/` is not read either, while a module path outside `hooks/` is HOOK-005.
- Handler code (`.ts … .py`) below `tests/`, `test/`, `fixtures/` or `node_modules/` under a plugin's `hooks/` or the project's `.claude/hooks/`, and a `.d.ts`, `*.test.*` or `*.spec.*` file there, is not read. A `.sh` file, or an executable file under the project's `.claude/hooks/`, is still read there as before.
- OMP extensions (`package.json` `omp.extensions`) are not audited: membrane audits Claude Code, Codex and OpenCode.
- HOOK-001's `| sh` has no end boundary, so `curl … | shasum` fires, in a script as in code (#1140).
- The secrets rules still do not scan `.mjs .cjs .tsx .jsx .mts .cts` files (#1141).
- A `local/` plugin, or one installed outside the cache layout, does not normalize to `@plugin:<plugin>@<marketplace>:`, so its `hooks/` code is not read, as its JSON hooks are not.
- A plugin named `unknown`, 7 to 40 lowercase hex characters (`deadbeef`) or a version string (`v1.2`) reads as a version name, so it does not normalize either: its `hooks/` code, its `hooks/hooks.json` and its `modules` are not read, with no finding. Its `.sh` files are read as before.
- A `.sh` file under the project's `.claude/hooks/` whose name holds a newline or tab, executable or not, is listed as in 0.7.2, split at that character: a Medium SCANNER-003 on the fragment.

## 0.7.2 (2026-11-08)

#1132 (SKILL.md step 8 passed a findings file to two renderers that took content), #1133 (nothing in the skill flow assigned display ids, so `--suppress SA-…` and `/apply-fix SA-…` never resolved) and #1135 (one registry entry that is not an object aborted four readers, and GC never ran again). One batch: the three share SKILL.md steps 6 to 8, the report functions, the registry readers and the documented-call test. Reading membrane's own findings files and state file, and numbering the ids it mints, is mechanical work on closed input (skill-first question 2); the step order in SKILL.md is prose.

### Fixed
- **#1132: the documented step-8 calls work.** `report_render_markdown`, `report_render_chat` and `report_assign_display_ids` read a findings file, or take the findings themselves, the same way `state_record_audit` does (a non-empty argument that does not start with `{` and names a file is read). Under `bin/csa` the documented calls exited 5 after a raw `jq: parse error`: chat printed nothing and the report file was left with a header, an all-zero table and no findings. Sourced, they exited 0 and rendered the path as one finding above an all-zero table, with no Critical listed. Passing the content instead was no fix: one argument is capped at 128 KiB, and a 700-finding scan measured 148 KiB (`Argument list too long`, exit 126).
- **#1132: input that is not findings JSONL is refused, exit 4.** A missing path, or any non-blank line that is not exactly one JSON object (`x`, `[1]`, `null`, two objects on one line, a valid line followed by `garbage`), prints one line, `csa: <file> is missing or is not findings JSONL (one JSON object per line); nothing rendered`, and exits 4 under `bin/csa` and sourced alike. No report file is written and no raw `jq:` text is printed; a line that cannot be read could be a Critical, so it is never skipped or counted as zero. An unreadable file prints that one line too (`csa: cannot read <file>; nothing rendered`), without `cat`'s own message beside it. Exit 4 is the code `suppress_stale` uses for the same input. An empty file is no findings, exit 0. SKILL.md step 8 says to report it and not record the run.
- **#1132: chat on findings over 64 KiB.** `report_render_chat` read the first display id with `printf | head -1`; under `bin/csa`'s pipefail, findings larger than a pipe buffer made it exit 141 with no output (now and then just over 64 KiB, every time well over it). It reads every line now.
- **#1133: display ids are assigned in the flow.** SKILL.md step 6 runs `csa report_assign_display_ids <baseline> "<report-name>"` after `baseline_tag`, where `<report-name>` is `<date>-<NN>` from `csa report_next_run_of_day`, so each finding's id is `SA-<date>-<NN>-<NNN>`, the prefix `state_record_audit` already recorded as `report_path_display_id_prefix`. Steps 7 to 9 read the numbered file, so chat and the report print the ids (not `SA-unknown`), the registry records them in `last_display_id`, and `--suppress SA-…` and `/apply-fix SA-…` resolve them.
- **#1133: one display-id lookup.** `suppress_add` and `apply_resolve_id` share it. An empty id matches nothing: `apply_resolve_id <root> ""` resolved to the first registry entry and exited 0, because every entry held `""`. A display id names a line of the latest recorded audit's report, so it resolves only to an entry seen in that run (`last_run_index` equal to the newest `audit_history` run index). An id that an older run's entry still holds matches nothing: when a report file is deleted, today's run numbers come round again, and the number a stale High still held could name a SCANNER finding of the new run (never registered), so `--suppress` on it stored the High's uid. Before, the first match in key order won, which could be the older finding. An id two entries of the latest run hold (only a hand edit makes one) matches nothing.
- **#1133: every id a report printed for a finding resolves to it.** A finding's uid has no line number, so one rule firing on the same text on two lines (`"Bash(*)"` listed twice, a prompt-injection line repeated) gives two findings with one uid, each printed under its own display id. The registry kept only the last of them, so the earlier ids were refused (`--suppress` exit 3 with a message that said no registered finding held them, `/apply-fix` exit 1), and a repeated Critical's earlier ids were refused as unknown instead of as Critical. Each registry entry now also lists every id the latest run printed for it, in `last_display_ids` (reset at the run's first sighting of the uid, appended on later sightings in that run); the lookup matches an id in that list or in `last_display_id`, still only for entries of the latest run.
- **#1133: a project's first audit is recorded.** Nothing created `.claude/audits/` before step 8, so on a project's first audit `report_render_markdown` and `state_record_audit` exited 1 (`No such file or directory`): no report, no recorded run, every finding lost from both, Critical included. `report_render_markdown` now creates its output file's directory and `state_record_audit` creates `.claude/audits/`; each exits 5 with one line (`csa: cannot create <dir>; no report written` / `… no audit state written`) only when it cannot. The same failure was in 0.7.1's flow.
- **#1135: one registry reader.** GC, re-sighting, `baseline_tag`, `apply_resolve_id` and `apply_run` read `state.json`'s `findings` through one definition. Readers skip an entry that is not an object (a string, a number, an array, `null`, a boolean), and the writers (`state_record_audit`, GC) drop it; a registry that is not an object reads as empty. Before, such an entry made every later audit record its run and then exit 5 in GC, so nothing aged again, and `apply_resolve_id` exited 5 silently for every display id. `suppress_add` keeps 0.7.0's exit 1 for such an entry.
- **#1135: three malformed fields.** GC evicts an entry whose `last_run_index` is not a number (it cannot be aged; it exited 5), reads a `rule_id` that is not a string as no rule (it exited 5), and a re-sighting counts a `seen_in_runs` that is not a number from 0 (it exited 5).
- **#1135: a failed GC leaves no `state.json.tmp.<pid>`** behind, and `state.json` as it was. Each aborted GC left a 0-byte one.

### Changed
- **The display-id form is `SA-<date>-<NN>-<NNN>`**, with the run of the day. The SKILL.md, `commands/apply-fix.md` and README examples show it. An id recorded in the old `SA-<date>-<NNN>` form still resolves by exact match.
- **The chat header's run number comes from the display ids** (`run #03` for `SA-2026-01-02-03-001`). It was always `run #01`. An id with no run number, or no id, still reads `run #01`.
- SKILL.md step 6 defines `<report-name>` and `<report-path>`, and step 8 writes `<report-path>`; the skill already wrote `.claude/audits/<date>-<NN>.md` but never said how `NN` is found.

### Migration
- **Display ids gain the run number.** The documented flow never recorded one (every `last_display_id` was `""`), so none already recorded changes. At its next sighting each entry gets `SA-<date>-<NN>-<NNN>`; one that is not seen again keeps `""`, which no longer resolves, and ages out.
- **Junk registry entries are dropped at the next audit.** An entry that is not an object, or one with no numeric `last_run_index` that does not fire, is removed, and a registry that is not an object restarts empty. A finding such an entry stood for reads NEW once and is re-created with `first_seen` = that run, so the 60 s suppression window applies to it again.
- **A registry that was stuck may evict many entries at once.** A state that made GC exit 5 has aged nothing since; its first working GC evicts, in that one run, every entry unseen for more than 10 scanned runs.
- **One additive registry field, `last_display_ids`**: each entry lists the display ids the latest run printed for its uid. It is written at the entry's next sighting; an entry without it reads as an empty list, and `last_display_id` is kept and written as before (the last id of the run). No reader keys on the set of fields of an entry, so `schema_version` stays 2, and a 0.7.1 or earlier membrane reading the file ignores the field.
- No finding uid changes; apart from `last_display_ids`, the state-file layout is unchanged.
- Exit codes: the three report functions on a findings file go from 5 (under `csa`) to 0, and on input that is not findings JSONL to 4; `state_record_audit`, GC and `baseline_tag` on a junk entry go from 5 to 0; `apply_resolve_id` goes from 5 to 0 or 1, and `apply_run` on a junk entry from 5 to 1. `suppress_add`'s codes are unchanged.

### Known limits
- A display id resolves only until the next recorded audit, which renumbers the findings; use the `FUID-` across sessions. An id from an older report exits 3 in `--suppress` and 1 in `/apply-fix`, even when that finding still fires under a new id. A deleted report file lets a run number, and so its ids, come round again in the same day's reports.
- Ids are assigned before the suppression filter, so a report's numbering has gaps where suppressed findings were left out.
- SCANNER findings get display ids, but they are not registered, so `--suppress` on one exits 3 and `/apply-fix` exits 1. `suppress_add`'s exit-3 message for an `SA-` id says so and points to the `FUID-`.
- `report_render_markdown` still exits 5 on a `<metadata-json>` that is not JSON (the model writes it), and the report header shows `metadata.run_of_day`, which step 8 does not tell the model to pass.
- Only GC removes its `state.json.tmp.<pid>` on a failed write. These writes still use `jq … > tmp && mv` (or `printf > tmp; mv` under errexit) and can leave one: `state_record_audit` (`lib/state.sh:339-340`), `state_update_self_integrity` (`:439`), `state_record_applied_fix` (`:591`), and `apply_run`'s two `applied_fixes` writes (`lib/apply-fix.sh:270`, `:299`). `state_record_audit` leaves one only if writing it fails (a full disk, under errexit); `state_update_self_integrity` and `state_record_applied_fix` are not called from the skill; the apply-fix writes need an auto-fixable rule, and none ships.
- Malformed `audit_history` (not an array, or entries that are not objects) and `applied_fixes` (not an array) are not guarded; GC on such a history exits non-zero and leaves the registry as it was, after `state_record_audit` has recorded the run.
- `csa_audit_harness` in the test helpers still runs the flow without the display-id step.
- The suite ran green on jq 1.8.1 and jq 1.7 (CI's) under bash 5.3. bash 3.2 was not run; the new lib code uses only forms 3.2 has (`[[ =~ ]]` with `BASH_REMATCH`, `$'\n'` in a pattern).
- 0.7.0's two Known-limit lines for #1132 and #1133 are history: both are fixed here.

When the read fails after a match was found, the rule emits that match and returns 0, because the engine drops a rule's output on rc 2; when it found none, it stops with a SCANNER-002. HOOK-004 matches the content it read before a `cat` error and emits if both patterns match; otherwise a clean prefix is not a clean file, so it is a SCANNER-002.
- **A failed `mktemp` or hook-entry walk is a SCANNER-002, not a skip.** The walk was cached run-wide even when it failed, which silenced HOOK-001 to HOOK-005 for the file; a failed walk is no longer cached, and each hook rule that reads the file reports it. A failed walk's partial output is discarded, not scanned. A failure to write the coverage `.target` file costs the coverage line a count, not the walk. A failed `mktemp` for a rule's target list is a SCANNER-002 for that rule.
- **threat-model.md** says what a finding with no line (the bare file) and one with a `json_path` (`file#path`) print.

### Tests
- `tests/test-fail-closed-readers.sh`: each stop above beside a control (a real non-match, a valid file, a readable target), the SCANNER-002 counts for a malformed settings file, and a match kept through a read error. `tests/test-dispatcher-rule-engine.sh` runs a malformed `settings.json` and a `chmod 000` target through `bin/csa` (`set -euo pipefail`). The unreadable-target tests skip when run as root. Each pin was mutation-checked, with these exceptions that the sourced tests cannot observe: the `rm -f "$cf.target"` cleanup after a failed coverage-file write (the test's failing target is a directory, which `rm -f` cannot remove either way; it is kept, as it removes a half-written file), and the `continue` after a failed per-rule `mktemp` (a sourced run without errexit skips the rule anyway; under the dispatcher a failing `mktemp` earlier in the scan aborts it, as before).

## 0.3.0 (2026-11-03)

**Hook commands declared in JSON are now audited (#427).** Before, a `curl ... | bash` in `.claude/settings.json`, or in an enabled plugin's `hooks/hooks.json`, gave zero findings: the hook rules read only scripts. Expect new findings, on first-party plugins too, the first time you audit after upgrading.

Skill-first question 3 (`docs/conventions/skill-first.md`): reading hook entries from JSON is mechanical work on open input (attacker-written command text), allowed as code because it can only add a stop and never approves anything. What it misses goes on to your own reading exactly as before. No model reads hook text.

### Added
- **`csa_hook_entries <file> <wrapped|plugin-manifest>`** (`lib/hook-entries.sh`) walks `.hooks.<Event>[i].hooks[j]` with `jq` and emits one JSON line per entry. `command` entries are decoded (JSON escapes; exec-form `args` joined into the checked text); other types are counted; each unreadable piece is an inconclusive line with its `json_path`. A `plugin.json` `hooks` field may be an inline event map, a path inside the plugin root (physical containment check; `./hooks/hooks.json` is a target already and is skipped) or an array of both.
- **Exact targets only:** the project's `.claude/settings.json` and `.claude/settings.local.json`, and a plugin's `hooks/hooks.json` and `.claude-plugin/plugin.json`. Never a nested `.claude/**/settings.json`, a plugin's `fixtures/` or `tests/` copy, or a plugin's root `settings.json`.
- **HOOK-001 to HOOK-004 read decoded commands** through a new `detect_text` entry point (one pattern per rule, shared with the file `detect`; HOOK-004 shares its two regexes). A match is a finding at line 0 with `context.json_path`; the `finding_uid` is built from 24 hex characters of the sha256 of the path and the full decoded command, short enough to pass `csa_redact` whole, so path and command length never hide a difference (the id itself is 32 bits, so two different commands share one only by a 32-bit collision), and reformatting the file changes nothing.
- **HOOK-005 `hook-entry-unreadable`** (High): a malformed file or a hook entry of the wrong shape is a finding, so a hook that went unread never reads as a clean audit.
- **HOOK-006 `hook-type-not-inspected`** (Info): one finding per file with per-type counts for `http`, `prompt`, `agent`, `mcp_tool` and later hook types.
- **A coverage line.** The engine prints `csa: hook-coverage checked=N flagged=N not-inspected=N unreadable=N` on stderr, the skill passes it to the report as `scope_summary`, and the report header prints it. `checked` counts every command entry matched against the HOOK patterns, and `flagged` those of them with a finding.
- Reports print `file#<json_path>` instead of `file:0:0` for a finding with a `context.json_path`.

### Known limits
- The patterns are the same common-pattern regexes as before; obfuscation still gets through. HOOK-002 (rm-rf) matches only `rm -rf` of an absolute path, so `rm -rf "$HOME"/x` is missed, in files and in hook entries alike; no pattern was widened.
- A handler script outside `.claude/hooks/` and the plugin directory is not read (the command that calls it is checked). `http`, `prompt` and `agent` hooks are counted, not inspected.
- User-level `~/.claude/settings.json` hooks are not read. Hooks in skill or agent frontmatter, inline hooks in a marketplace entry, managed-policy hooks, and Codex or OpenCode hook formats are not read.
- A plugin whose files do not normalize to `@plugin:<plugin>@<marketplace>:` (a `local/` plugin, an install record pointing outside the cache layout) has its JSON hooks unread.

## 0.2.0 (2026-11-02)

**Audits now scan your enabled plugins, so a first real run reports more.** On a real Claude Code install the scanner read no enabled plugin at all, and said nothing about it: a clean audit and a skipped one looked the same (#825). Expect new findings, on first-party plugins too, the first time you audit after upgrading.

### Fixed
- **`enabledPlugins` is read as Claude Code writes it.** It is an object map, `{"plugin@marketplace": true|false}`; the scanner only knew an array of names and read the object as empty. Only boolean values count, `false` means not enabled, and the array form still reads (each name as `true`). The user's `settings.json`, the project's, then the project's `settings.local.json` merge by key, the later file winning, so a project `false` disables a user `true`. A plugin's identity is the whole `plugin@marketplace` key. `settings.local.json` is a new read.
- **Each enabled plugin resolves to where it is installed.** The scanner looked for `cache/<plugin>/<version>`; Claude Code uses `cache/<marketplace>/<plugin>/<version>` and records every install in `~/.claude/plugins/installed_plugins.json`. The scanner now takes this project's `local` or `project` entry (its `projectPath` is the project root), else the `user` entry. An `installPath` is used only if it is a directory physically inside `~/.claude/plugins/`; one that points elsewhere (a `..`, a symlink out) is PROVENANCE-002. With no record entry it falls back to the cache layout, and a name part holding `/` or `..` is refused. An `installed_plugins.json` that exists but cannot be read or is not the shape this code knows stops the audit (rc 2), never an empty set.
- **PROVENANCE-002 is a finding.** An enabled plugin that does not resolve was a stderr line that a successful scan dropped. It is now a High finding that names the plugin and why, recorded in `state.json` and reported like any other, and a later audit that resolves it removes it from the report.
- **A plugin finding's id survives a version bump.** `FUID` paths for `cache/<marketplace>/<plugin>/<version>/...` now normalise to `@plugin:<plugin>@<marketplace>:...`; the older two-level form is unchanged. No stored id needs migrating: a real install never scanned a plugin, so no real finding used the old form.
- **Paranoid-mode candidates are plugins, not marketplaces.** They are the install record's keys plus each `cache/<marketplace>/<plugin>` as `plugin@marketplace`, minus the enabled set; a `false` plugin is a candidate. `temp_git_*` (a clone in progress) is skipped.
- **The SessionStart reminder's "enabled-plugin set changed" note is true.** `state.json` stored an empty snapshot whatever was enabled, and the hook read the object map's values (`true`, `false`) instead of names. The audit now records the enabled set and the hook compares the same set. After upgrading, each session's reminder may print a false "changed" note until the next audit rewrites the snapshot.

### Added
- **A loud warning for a shape the reader cannot use.** An `enabledPlugins` value that holds entries but yields none (a string, an array of non-strings, an object of non-booleans) prints `csa: warning: ... unrecognized shape (...)`, since Claude Code can change this format.
